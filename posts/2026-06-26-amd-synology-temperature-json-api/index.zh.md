# 别再相信单一温度来源：我给 AMD 群晖做了一份可验证的温度 JSON

![AMD 群晖温度接口和桌面小屏](cover.png)

> **一句话结论：** 监控不是“读到一个数”就结束了。一个没有第二来源核对过的温度，只是一个看起来很官方的数字。

## TL;DR

| 难点 | 我的做法 |
| --- | --- |
| Glances 读不到主板温度 | 主板/系统温度走 DSM 自己的 `synowebapi` |
| AMD CPU 不叫 Core 0 | CPU 读 `k10temp` 的 `Tctl`，回退 `Tdie` |
| 群晖自带 `smartctl` 半残 | 硬盘显式 `-d sat` 读 SMART 属性 |
| 单一管线可能自洽但错误 | 每次运行用独立来源交叉验证 |
| 下游设备需要稳定契约 | 输出一份扁平 JSON，原子写入 |

---

## 1. 为什么这件小事会变复杂

**小结论：** AMD 群晖不是“读温度教程”的默认模型。

我最初只是想在桌上摆一个小屏，看 NAS 的温度：CPU、系统、每块硬盘。听起来像一个下午能搞完的事，结果 AMD 群晖一次性打破了几个常见假设：

| 常见假设 | 在 AMD 群晖上的现实 |
| --- | --- |
| `smartctl --json` 好用 | 自带版本老，没有 JSON，`--scan` 也不好用 |
| CPU 有 `Core 0` | AMD `k10temp` 里是 `Tctl` / `Tdie` |
| Glances 能读全硬件 | 它能看到 CPU，但不稳定地看到主板和硬盘 |
| 一个工具能包圆 | 每个工具都缺一块，而且缺的不是同一块 |

所以这不是“找一个命令”的问题，而是“把几个不完整来源拼成一个可信接口”的问题。

## 2. 每个值挑最可靠的来源

**小结论：** 不要逼一个工具做所有事，让每个数来自最擅长报告它的地方。

| 值 | 来源 | 读取方式 |
| --- | --- | --- |
| CPU | Glances REST API | `.../api/4/sensors`，标签 `Tctl`，回退 `Tdie` |
| 系统 / 主板 | DSM Web API | `SYNO.Core.System` -> `sys_temp` |
| 硬盘 | `smartctl` | `-A -d sat /dev/sataN`，属性 `194` 或 `190` |

采集器只做三件事：

1. 从这三个来源读取温度。
2. 统一成整数摄氏度。
3. 写出一份扁平 JSON。

如果某个来源不可用，对应字段就是 `null`。我宁可显示“没有数据”，也不编一个看起来合理的数字。

## 3. 别信任自己的管线

**小结论：** 最有价值的不是采集，而是验证。

大多数 homelab 监控是自洽的：它读一个工具，然后把那个工具的结果画出来。问题是，自洽不代表正确。

所以我给它加了 `verify.py`，每次运行都把接口输出和独立来源对账：

| 字段 | 接口来源 | 交叉验证来源 |
| --- | --- | --- |
| CPU | Glances | 直读 sysfs：`/sys/class/hwmon/.../temp1_input` |
| 系统 | JSON 输出 | DSM `synowebapi` 的 `sys_temp` |
| 硬盘 | `smartctl` | DSM Storage Manager |

验证留 `3°C` 容差，用来吸收两次采样之间的时间差。任一项不一致，脚本就非零退出。

> 监控的重点不是“我能读到”，而是“我能证明它没读错”。

## 4. 输出契约：一份小 JSON，喂给所有下游

**小结论：** 下游越简单，接口越应该稳定。

最终输出是这样：

```json
{
  "ts": 1750900000,
  "unit": "C",
  "model": "DS1525+",
  "cpu": 53,
  "cpu_label": "Tctl",
  "system": 41,
  "disks": [
    { "name": "sata1", "temp": 38 }
  ]
}
```

我特意让它扁平、短、好解析。守护进程每 30 秒刷新一次，并且**原子写入**：先写临时文件，再 `mv`。这样 ESP32 或网页永远不会读到半截 JSON。

下游现在有两个：

- 一个自包含的网页表盘。
- 一个 ESP32 / M5Dial 桌面小屏，按 `ts` 判断数据是否过期。

## 5. 踩坑 / 修法

| 坑 | 原因 | 修法 |
| --- | --- | --- |
| 脚本把自己杀了 | BusyBox 没有 `pgrep`，`pkill -f` 匹配到启动器自己 | 用 PID 文件，按 PID kill |
| Docker 里 CPU 传感器为空 | 容器看不到宿主机硬件传感器 | Glances compose 加 `pid: host` |
| `scp` 连不上 DSM | 群晖没启用现代 `scp` 默认走的 SFTP 子系统 | 用 `scp -O` 走旧协议 |
| 硬盘温度读不到 | 自带 `smartctl` 需要显式设备类型 | `smartctl -A -d sat /dev/sataN` |

这些坑看起来都很小，但它们共同说明了一件事：NAS 监控不能只靠“网上教程说这么写”。

## 6. 取舍

**小结论：** 这是一个锋利的小工具，不是通用企业监控平台。

- 它是按一台 AMD 群晖调的，硬盘槽位、`Tctl`、`hwmon` 路径目前都有机器假设。
- 它只做温度，吞吐、风扇、UPS、容量还没纳入。
- 端点只应该放在内网，不该端口转发，也不该裸露公网。
- 真机 M5Dial 固件还在迭代，今天最稳定的是 JSON 契约和网页表盘。

## 7. 可复制清单

- [ ] 先列出每个温度字段的可信来源。
- [ ] 不要用一个工具强行读所有东西。
- [ ] 对每个字段找第二来源交叉验证。
- [ ] 输出 JSON 时允许 `null`，不要编假数。
- [ ] 原子写入文件，避免读到半截。
- [ ] 下游用 `ts` 判断数据是否过期。
- [ ] 端点只放内网，别暴露公网。

## 8. 最后

这个项目真正想解决的不是“怎么显示温度”，而是：

> 当一个数字会影响你的判断时，你有没有办法证明它值得信？

在 AMD 群晖这种温度散落在三个半残工具里的平台上，这份 JSON 至少给了我一个能解释、能验证、能喂给小屏的答案。
